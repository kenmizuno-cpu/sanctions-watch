# 暗号資産アドレス監視：運用・導入

## 収録範囲

Crypto-1としてOFAC SDN Advanced XMLの明示アドレスを収録する。対象者ID、通貨記号、原文、原本内位置、プログラム、原本SHA256を残す。人物名マスターにはアドレスを入れない。自動凍結・制限解除・社内承認処理を含めない。

保存済み正常原本を再利用し、新たなOFACへの通信は行わない。OFAC workflowの完了後と毎時47分に、別の`watch-crypto`で収録する。収集コード・専用テスト・workflow自体のmain反映時にも実行し、配布データのコミットでは再起動しない。既存OFACの毎時監視頻度は変更しない。

出力：`data/crypto/dashboard.json`（単一版配布JSON）と`data/crypto/address_master.json`（掲載関係台帳）。人物名の配布ファイルは変更しない。検証未対応・不正形式も公式原文を台帳へ保持し、要確認に表示する。これらを検証済み照合索引へ登録したものとは扱わない。

## コード管理と会社での運用（2026-10-07の方針）

会社のスプレッドシートを運用先とし、設置と更新の適用は利用者が行う。コードの修正・検証・GitHubへの反映は、このWorkで継続して管理する。

| 担当 | 作業 |
| --- | --- |
| このWork | 共通コードの修正・検証・GitHub更新、変更内容と差し替え用ファイルの提供 |
| 利用者 | 会社のシートへの設置、Google権限承認、トリガー設定、更新コードの差し替え、動作結果の確認 |

共通コードの原本は `kenmizunokuro/sanctions-watch` のmainにある `apps_script/crypto_dashboard/` とする。会社側でも同じ9つの `.gs` と `appsscript.json` を使用し、機能別のファイル分割を維持する。更新時は対象コミット、変更ファイル名、差し替え用の全文、変更内容、確認結果をまとめて渡す。複数ファイルにまたがる変更は、同じ版のファイルをまとめて適用する。

GitHubのコードを更新しても、設置済みのApps Scriptコードには自動反映されない。利用者が会社側のプロジェクトへ更新を適用する。シートID等の設置先固有の値は設定タブやScript Propertiesで管理し、共通コードへ会社別の修正を加えない。

上記の初期確認用シートは参考用であり、会社の運用シートの設置完了を示すものではない。

## Apps Scriptの設置

1. 会社で運用する監視スプレッドシートを開き、「拡張機能 → Apps Script」を開く。
2. 下表の9つのスクリプトファイルを同じプロジェクト内に作り、それぞれ同名`.gs`の内容を貼る。Apps Scriptのファイル名では`.gs`を自分で二重に付けない。ファイルの読込み順への依存はない。
3. プロジェクト設定で「appsscript.json マニフェスト ファイルをエディタで表示する」を有効にし、同梱の`appsscript.json`を貼る。
4. `setupCryptoDashboard`を一度実行し、必要なGoogle権限を承認する。初回同期が成功した後、15分ごとのトリガーが作られる。
5. シートを開き直すと「アドレス監視」メニューが表示される。「今すぐ同期」で確認し、同期履歴に成功が記録されることを確認する。

コネクターによるスプレッドシート作成・初期データ反映と、Apps Scriptの設置・権限承認は別工程。初期データが見えていても定期同期済みとは限らない。

| ファイル | 修正する機能 |
| --- | --- |
| Config.gs | リポジトリ・ブランチ・閾値・シート名 |
| Fetch.gs | SHA固定のJSON取得・通信制限 |
| Validate.gs | 配布版・件数・ID・日時・文字列検証 |
| Store.gs | タブ書込み・失敗時の旧内容復旧 |
| View.gs | 日本語表示・日時・レイアウト |
| History.gs | 同期履歴・同期障害表示 |
| Sync.gs | 全工程の実行順・ロック・成功記録 |
| Triggers.gs | 初期設定・15分実行・停止 |
| Menu.gs | 操作メニュー |

「設定」タブの値だけ手動変更できる。自動管理タブに書いたメモは同期で消えるため、メモが必要なら新しいタブを作る。レビュー表は確認用で、承認結果をここからマスターへ反映する機能は未実装。

GitHubは公開リポジトリのみを対象とし、トークンをシートへ保存しない。ブランチのコミットSHAを解決してその版のJSONを取得する。全データ検証後にタブを更新し、失敗時は書きかけのタブを含め復元を試みる。復旧も失敗した場合はエラーメッセージにタブ名を残す。

同期上限は5MB・台帳5000行・イベント30000件。将来超える場合は分割配布・履歴の世代保管を設計して上限を更新する。上限超過を「差分なし」としない。初回収録・補完は差分タブに出さず、イベント証跡としてJSONに保存する。

## 自動検証（2026-10-07追加）

Bitcoin（XBT）のBech32／Bech32mと、Ethereum（ETH）のEIP-55をGitHub側で自動検証する。原文・対象者・原本証跡・掲載関係IDを保持する。会社側に検証ライブラリを設置する必要はない。

- Bitcoin：mainnetの接頭辞、文字、大小文字、長さ、余剰ビット、witness版とチェックサム方式を確認する。
- Ethereum：混在した大小文字をKeccak-256によるEIP-55と照合する。全小文字・全大文字・数字だけの場合は「形式正常・チェックサム情報なし」として要確認を維持する。チェックサム不一致の原文を補正して正常扱いしない。
- USDT等：通貨記号だけではネットワークを確定できないものは未確定を維持する。未対応通貨を推測で正常化しない。

「アドレス台帳」と「要確認」に検証方法・詳細・版を追加する。検証結果のみの更新は公式掲載差分とは別の検証履歴に記録する。詳細な検証器・固定テスト・初回原本の確認結果は[自動検証の記録](crypto-validation-20261007.md)を参照。

会社側で今回差し替えるファイルは同じ版の `Validate.gs` と `View.gs`。保存後に `setupCryptoDashboard` を再実行し、初回同期・新しい列の書式・15分トリガーを設定する。既存の設定タブの値は保持する。以後は「今すぐ同期」でも更新できる。従来の9ファイル構成とマニフェストは維持する。

## 監視状態

- 台帳収録成功：保存済み原本の検証・抽出・保存が通った。
- 上流監視：実際のOFAC取得記録を使用。収録実行日時では更新しない。
- スプレッドシート同期：JSONの取得・検証・全タブ書込みが通った。
- 形式・ネットワーク要確認：ネットワーク未確定、形式検証未対応、形式不正等。犯罪関与の認定ではない。
- 掲載終了候補：原本から掲載関係が消えた候補。旧原文を残し、制限解除を行わない。

遅延警告は上流最終確認から120分、重大は360分（設定変更可）。Sheetsの15分同期は、公式更新を15分以内に検知したという意味ではない。取得情報のETagやHTTP更新日時を指定日や発効日に代入しない。

## HTTP取得エラーの切り分け

`Fetch.gs`のHTTPエラーには、取得先URLと工程（GitHub版確認／配布JSON取得）を表示する。GitHub APIの応答ヘッダーまたは応答理由が回数制限を示す場合のみ、回数制限と再開目安（UTC、応答に含まれる場合）を表示する。403という番号だけで原因を断定しない。

導入時に取得エラーが出た場合は、最新版の`Fetch.gs`へ差し替え、`setupCryptoDashboard`を再実行してエラー全文を確認する。初回同期に失敗した段階では15分トリガーは未設定なので、初回設定を成功させる必要がある。原因確認前に連続実行やトークンの外部共有を行わない。

## 手動実行・検証

```bash
python -m src.crypto_watch
python -m unittest
node tests/test_crypto_dashboard.cjs
```

原本ハッシュ不一致、空抽出、参照表・対象者IDの異常、20%以上の件数減少は台帳反映を停止し、配布JSONを失敗表示へ更新する。前回の台帳・最終成功日時を保持する。保存そのものが不可能な場合はworkflow失敗と失敗証跡で確認する。
