# OFAC監視の遅延対策

2026-10-01の調査で、9/29–9/30の毎時実行は9/48回に減少した一方、直近15実行は成功し、runner開始まで2–3秒だった。対策の主眼はGitHub scheduleとは別の起動・通知経路である。ユーザーの「ではその対策をしようか」に基づき、調査報告の推奨を実装する。

## 構成

- 専用のGoogle Apps Scriptプロジェクトに `apps_script/OfacWatchdog.gs` を配置する。既存シート同期とはプロジェクトを分ける。
- 10分間隔の外部トリガー。GitHub Contents APIでmainの今月・前月のheartbeatを取得し、SDN/Consolidatedの両方が同一時刻に成功した最終チェックを使う。304、変更なし、削除レビュー待ちは成功として扱う。エラー行、片方だけの成功、将来時刻は鮮度を更新しない。
- 75分超で `watch-ofac.yml` をworkflow_dispatch。稼働中・待機中のOFAC実行があれば追加起動しない。受理後30分は再起動を抑制する。
- 90分超で警告、150分超で重大のメール。実行失敗とAPI/認証障害も通知。状態変化・復旧時と障害継続6時間ごとに通知し、送信失敗を通知済み扱いにしない。
- トークンはGAS Script Propertiesに限定。対象repoのみActions read/write、Contents read。メール先も設定必須。セットアップはAPI読取・通知テストが成功してからトリガーを作成する。
- 取得実行の成否を `data/monitoring/ofac_attempt.json` に記録する。失敗時のCI保存はこのファイルだけを別のクリーンなcheckoutからコミットし、部分更新されたmaster/state等をpushしない。既存失敗Artifactは維持する。
- HTTP 429/502/503/504と接続・読取timeoutを合計3回まで再試行。待ち時間を制限し、既存ネットワーク禁止先・リダイレクト検証・条件付きGETを維持する。
- Slack未設定をActions警告と送信結果に明示し、監視の成功と通知配信を区別する。

## 運用上の限界

GASにも時刻保証はない。10分は設定間隔で、最大検知時間やSLAの保証ではない。GitHub API/Actionsが停止すると取得処理自体は実行できないが、GASのメール通知経路は残る。トリガー作成と認証許可はGAS所有者が行う。導入前後の90分超滞留割合、最大成功間隔、dispatch受理から成功までを比較する。
